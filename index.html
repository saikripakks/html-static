Step-by-Step Deployment Guide

Follow the standard Git-based deployment workflow used to publish this static website to GitHub Pages.

01
📄

Create index.html

Design a clean semantic HTML structure with modern responsive CSS and interactive components.

touch index.html css/style.css
02
🚀

Push to GitHub Repo

Initialize the repository, stage changes, commit, and push the branch to your remote GitHub repository.

git push -u origin main
03
⚙️

Open Repo Settings

Navigate to your repository on GitHub, click the Settings tab, and select Pages in the left sidebar.

Settings → Pages
04
🌿

Select Branch & Folder

Under Build and deployment, choose Deploy from a branch. Select main branch and / (root) folder, then click Save.

Source: Branch 'main' / (root)
05
🔗

Access Live Website

GitHub triggers an automated deployment workflow. Within 1-2 minutes, the live URL is active and secured with HTTPS.

https://<user>.github.io/<repo>/
06
🎨

Customize with CSS

Iterate styling, add CSS custom variables, dark/light themes, animations, and commit to update in real time.

git commit -am "style: update UI"

DevOps Concepts

Static Hosting vs Dynamic Hosting

Understanding why static website hosting on GitHub Pages is resilient, cost-effective, and secure.

Criteria GitHub Pages (Static Hosting) Traditional / Dynamic Hosting
Hosting Cost 100% Free (within usage limits) Monthly cloud compute/server costs ($5 – $500+)
Server Management Serverless / Zero server maintenance required Requires patching OS, monitoring, load balancers
SSL/TLS Certificate Automatic HTTPS provided by GitHub Manual setup (Certbot / AWS ACM / Nginx config)
Deployment Trigger Native Git push via built-in GitHub Actions Requires external CI/CD pipelines (Jenkins, GitLab CI)
Backend Logic / DB Client-side only (HTML, CSS, JS, external APIs) Server-side runtime (Node.js, Python, PHP, SQL DBs)
Attack Surface Minimal (no server vulnerabilities, no SQL injection) High (server exploits, DB leaks, runtime flaws)

Interview Questions & Detailed Answers

Comprehensive explanations for all 7 key interview questions from Task 6.

GitHub Pages is a free static web hosting service provided by GitHub that takes HTML, CSS, and JavaScript files directly from a repository, runs the files through a build pipeline (optionally using Jekyll or custom GitHub Actions), and publishes a website hosted on GitHub's global Content Delivery Network (Fastly CDN) with automated SSL/TLS encryption.
No, you cannot execute server-side dynamic applications (such as PHP, Node.js/Express, Python/Django, Ruby on Rails, or Java backends) directly on GitHub Pages because there is no server-side application runtime or direct database connection.

However: You can host Single Page Applications (SPAs built with React, Vue, Angular) and static site generators (Next.js static export, Gatsby, Hugo, Astro) as long as they compile to static HTML, CSS, and JS. Dynamic data can still be fetched client-side by calling external REST APIs or serverless functions (like AWS Lambda or Supabase).
GitHub Pages is subject to specific usage guidelines and limits:
  • Repository Size: Recommended to stay under 1 GB.
  • Site Size: Published sites cannot be larger than 1 GB.
  • Bandwidth: Soft limit of 100 GB per month.
  • Build Limit: Maximum of 10 builds per hour.
  • Commercial Restrictions: Prohibited from running high-frequency commercial e-commerce transactions or malicious operations.
Updating the website follows the standard Git workflow:
  1. Make code changes locally to files like index.html, style.css, or scripts.
  2. Stage and commit the changes: git add . && git commit -m "Update website content".
  3. Push the commits to the publishing branch: git push origin main.
GitHub Pages automatically triggers a background deployment workflow to re-build and re-publish the site within 1 to 2 minutes.
When the repository hosting the GitHub Pages site is deleted:
  • The associated GitHub Pages website is immediately taken offline and permanently deleted from GitHub's servers.
  • Any visitors navigating to the live URL will receive an HTTP 404 Not Found error.
  • Any custom domain configuration attached to the repository is released.
The default file that loads when a user visits the root directory is index.html (or index.md if Jekyll markdown processing is enabled).

Additionally, if GitHub Pages encounters an invalid route, it will automatically serve a custom 404.html page if present in the root of your publishing branch.
Yes, custom domains are fully supported.

To configure a custom domain (e.g., www.mydevopsportfolio.com):
  • Add CNAME file: Create a CNAME file in the repository containing your domain name, or enter the domain in repository Settings → Pages → Custom domain.
  • DNS Configuration: In your DNS provider (e.g., Cloudflare, Route53, Namecheap):
    • For apex domains (example.com): Add A records pointing to GitHub's Anycast IP addresses (185.199.108.153, 185.199.109.153, 185.199.110.153, 185.199.111.153).
    • For subdomains (www.example.com): Add a CNAME record pointing to <username>.github.io.
  • Enforce HTTPS: Check "Enforce HTTPS" in GitHub Pages settings to generate a free Let's Encrypt SSL certificate.
